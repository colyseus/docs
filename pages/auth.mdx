# Authentication

Colyseus authenticates clients on two surfaces: **room joins** (via an `onAuth` hook) and **HTTP routes** (via middleware). The official [`@colyseus/auth`](/auth/module) module powers both surfaces and pairs with [`@colyseus/database`](/database) for a zero-config user store, automatic route mounting, and revocation-aware sessions.

<Callout type="info">
    **Fastest setup:** add a `GameDatabase` to `defineServer` and `@colyseus/auth` wires itself — user store, register/login routes, ban gating, and revocation-aware JWTs, all from one option. → [Database → Authentication](/database#authentication-built-in-colyseusauth-integration)
</Callout>

## Common scenarios

### Authenticate a room join

Colyseus exposes an `onAuth` hook that runs before a client joins a room. It receives the token sent by the client so you can verify it, reject invalid sessions, and forward user data into `onJoin`. With the database integration active, the default `onAuth` already verifies JWTs and rejects revoked sessions (bans and `bumpTokenVersion()` both invalidate live tokens at the token layer) — you only need to override `onAuth` for room-specific logic on top.

### Protect an HTTP endpoint

Colyseus ships a single authentication middleware that gates any endpoint behind a valid JWT. It works with both Express handlers and the typed HTTP routes system, and exposes the verified user payload to your route handler. When the database integration is active, the same middleware also enforces session revocation — no per-route bookkeeping required.

### Revoke a session or force-logout a user

With `@colyseus/database`, every JWT carries a per-user version. `db.auth.ban()` bumps that version atomically with the ban fields, so a banned user's existing tokens are rejected on their next verification — *and* new login attempts are gated via `onCheckBanned`. For non-ban scenarios (password change, suspicious activity, manual "sign out everywhere"), call `db.auth.bumpTokenVersion(userId)` directly.

### Bring your own database

The integration with `@colyseus/database` is optional. `@colyseus/auth` exposes a set of backend callbacks — find user, register, hash password, send email, OAuth lookups — that you implement against your own storage. Every flow described on this page works without the database package; you trade zero-config wiring for full control over the data layer.

### OAuth, anonymous login, and password reset

All supported out of the box. The module bundles 200+ OAuth providers (Discord, Google, X, …), anonymous-user registration, and forgot/reset password flows with customizable email templates. With `@colyseus/database`, the persistence side is already wired — you only need to configure providers and email delivery.

### Customize individual callbacks

The database integration exposes its callback set as an extensible bag — override any individual hook (e.g. to add an invite-code check on registration, or to customize the anonymous user payload) while keeping the rest of the wiring intact. You get a defaults-plus-overrides composition rather than an all-or-nothing choice.

### Use the frontend client SDK

The `@colyseus/auth` client SDK provides typed methods for register, sign-in (email/password, anonymous, OAuth), password reset, and sign-out. The auth token is stored on the client and sent automatically on subsequent room joins and HTTP requests, so you generally don't manage it by hand.
